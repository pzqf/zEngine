# ADR-001：通用事务协调器只保留为进程内实验机制

**状态**：Accepted

**日期**：2026-09-01

**关联任务**：zMmoServer `CON-03`

## 背景

`zConsistency/transaction.go` 提供一个内存两阶段协调器。它保存 participant、vote、prepared 和终态，
但没有 durable log、恢复扫描、稳定跨进程事务 ID、participant 幂等协议或 fencing。协调器进程在
prepared 后崩溃时，无法恢复并继续提交，因此不能作为生产级分布式事务实现。

调用图确认：zEngine 只有测试构造该类型；zMmoServer 仅在 `MigrationManager` 的可选公共参数中引用它，
仓库内没有生产构造，现有迁移测试也全部传 `nil`。玩家迁移需要持久领域状态机、owner/epoch CAS 和明确
commit point，不能靠扩充这个通用内存对象获得正确性。

## 决策

1. 新的准确名称为 `InMemoryTransactionCoordinator`，并明确标记为 experimental、仅限单进程。
2. `TransactionManager`、`TransactionManagerOption` 和 `NewTransactionManager` 暂时保留为 deprecated
   源兼容入口；本任务不在同一变更中删除公共 API。
3. 协调器必须原子占有 Prepare/Commit 状态转换，`State/Votes/Prepared` 的内部读写统一加锁；
   participant callback 在锁外执行，并提供并发安全 snapshot 读取。
4. 本机制不增加 WAL、恢复扫描、跨进程 participant/fencing，也不声明 exactly-once 或崩溃恢复。
5. `MIG-02` 应实现迁移领域状态机。该状态机替代 zCommon 的可选协调器参数并经过兼容窗口后，再单独退役
   旧别名和实现。

## 未选择方案

- **扩建 durable 通用协调器**：没有独立生产调用者，且迁移的 owner、route CAS、补偿和恢复是领域语义；
  此时建设通用 WAL 会增加未经真实负载证明的机制和双重状态机。
- **立即删除**：zCommon 公共构造仍暴露旧类型。原地删除会把并发修复、上层 API 迁移和兼容破坏混在
  一个任务中，不符合公共 API 演进纪律。

## 结果与限制

该协调器可以作为单进程编排、测试和教学原语，但调用者必须接受进程退出即丢失全部状态。`Prepared`
不等于可恢复，`Committed` 只描述当前进程内 callback 返回结果。任何跨进程持久工作流仍需独立的 durable
领域状态、幂等 participant、唯一提交点和恢复证据。

## 验证

- zEngine：并发 Prepare/Abort、重复 Prepare、重复 Commit、Vote/Cleanup/snapshot 的 `-race` 测试；
- zMmoServer：zCommon migration 编译与全量 `-race` 回归，证明 deprecated 兼容入口未破坏现有调用；
- 文档和全模块 build/vet 门禁；不以本任务声称 E3/E4/E5。
