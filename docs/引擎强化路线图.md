# zEngine 强化路线图（zMmoServer 能力下沉）

> **这份文档是什么**：zMmoServer 在真实 realm MMO 压力下，把一批 **game-agnostic 的分布式/并发承重件**
> 在应用层（zCommon）实现了出来——它们本该是引擎能力。本路线图记录「把它们回归 zEngine」的工作：
> 已落地的、以及按收益排序的后续项。
>
> **一条铁律**：下沉不得引入反向依赖（引擎零 import 应用层）；只沉机制，业务枚举/胶水留在应用；每项挂测试。
>
> **版本**：0.0.1 ｜ **创建**：2026-07-27。

## 一、本轮已落地

| # | 能力 | 位置 | 是什么 / 为什么 | 背书 |
|---|------|------|----------------|------|
| 1 | **zActor.Runner**（单写者闭包串行器） | `zActor/runner.go` | 补 `BaseActor` 缺的三块：**同步 `Do`（请求-响应，拿返回值）** + **`PostTick` 合帧投递（满帧丢弃，latest-wins）** + **每命令 panic 隔离**。这正是 zMmoServer 的 `map_actor` 自造、而 BaseActor 不具备的能力。BaseActor（类型化消息+监督）保留不动，两种范式并存 | `runner_test.go` 6 用例 |
| 2 | **zInstance.Pool**（实例池 + 在途预留额度） | `zInstance/pool.go` | 「按需创建、空置自动回收的实例池」——房间/副本/战场/匹配/分线的最大公约数。封装了一个**通用且极易写错的并发点**：`reserved` 在途预留额度，消除「读占用→选中→加入」的 TOCTOU 与「空置回收 vs 正在加入」的竞态 | `pool_test.go` 4 用例（含并发不击穿 cap） |
| 3 | **zAoi**（网格视野） | `zAoi/`（原 `zCommon/aoi`） | 引擎最大空白——MMO 核心原语，此前引擎完全没有（`zNavMap` 是寻路≠视野）。纯 2D 空间索引 + 九宫格视野 + enter/leave/move 事件，无玩法耦合 | `grid_aoi_test.go` |
| 4 | **zHealth**（健康检查框架） | `zHealth/`（原 `zCommon/health`） | 可插拔 Checker 框架（Memory/Goroutine/Disk/Time/GC）。与 `zServer`/`zMetrics` 互补不重叠 | build 绿（原无测试） |
| 5 | **zConsistency**（Outbox/Inbox + 2PC） | `zConsistency/`（原 `zCommon/consistency`） | 分布式可靠性硬通货——引擎此前只有 `zDistributed` 锁。事务性 outbox/inbox（内存+SQL 双实现，driver-agnostic）+ 2PC 事务管理器，跨进程 exactly-once/幂等 | `memory_store_test`/`transaction_commit_test`（内存）、`sql_store_test`（需 MySQL DSN，未设即 Skip） |

**下沉三包（3/4/5）零反向依赖**：均只依赖 `zEngine/zLog` + `zUtil/zMap` + 标准库，不 import 任何 zCommon 子包。
zMmoServer 侧改了 9 处 import（`zCommon/{aoi,health,consistency}` → `zEngine/z{Aoi,Health,Consistency}`，用别名保持引用体不变）。
zEngine go.mod 为测试补了 `testify`（zAoi）+ `go-sql-driver/mysql`（zConsistency SQL 测试）。

## 二、后续路线图（按收益，需解耦/收敛/替换，未在本轮做）

这些价值高但需要更大改动或牵动业务，留作后续、逐项挂测试推进：

1. **MapServer 回归引擎**：用 `zActor.Runner` 替换自造 `map_actor.go`、用 `zInstance.Pool` 替换 `instance_manager.go` 的实例池部分。删自造件、消除重复。（本轮已提供引擎能力，替换是下一步——需完整回归 + t1 `-race`。）
2. **discovery → zEngine**：填「zDistributed 只有锁、无服务发现」的空白，用量最高。需先**剥离 `common/id` 的 MMO ServerID 编码 + `MapIDs` 业务字段**，只沉泛型 `ServiceDiscovery`/`StatusManager` 接口，MMO 包装层留应用。
3. **connpool + NetPacket 池归位 `zNet`**：客户端连接池 + `NetPacket` 对象池本就是 zNet 该有的；`pool` 需先删对 `gameevent` 的业务依赖。
4. **gameevent 与 zEvent 收敛**：当前两套事件系统并存（gameevent 不 import zEvent、自造 5 级优先级+命名，而部分代码仍用 zEvent）——明确重复。把优先级/命名增强进 `zEvent`，择一收敛。
5. **parallel（分区 tick 调度器）**：纯净可下沉，但当前 0 接线——**下沉前先在应用真正用一次验证**，避免把未验证代码搬进引擎。
6. **异步 RPC 关联器 + 东西向报文层**：`crossserver.RequestRouter`（reqID→pending chan + 超时）+ `Envelope`（40B 节点间头）合并做成 `zNet` 的「节点间可靠请求-响应」。**佐证**：`crossserver/rpc.go` 用 JSON 而同包 `codec.go` 明令禁 JSON——自相矛盾正说明缺引擎级统一 RPC 层。
7. **ID 机制进引擎**：`Snowflake`（含时钟回拨处理）+ `ServerID` 语义编解码 + `TypedID[Tag]` 泛型基座下沉为基础设施；**20+ 业务类型枚举（Pet/Mount/Auction…）不搬**，留应用声明。
8. **收敛/并入既有模块**：`monitor` → `zMetrics`；`lifecycle` → `zServer`/`zService`（其重叠的是生命周期编排，非 zObject）；`container` 弃用（`zInject` 已覆盖 DI）。

**不下沉**（纯业务）：`cache`（MMO 字段）、`game`（领域对象）、crossserver 的 MMO 语义部分、serverconnmgr（太薄，zNet 已覆盖）。

## 三、下沉原则（沉淀）

- **单向依赖**：引擎零 import 应用（`grep` 已验证 zEngine 不 import zCommon/zMmoServer）。下沉前先查目标包是否 import 了 zCommon——若有则先解耦。
- **只沉机制，留业务**：把业务枚举、语义包装、接线胶水留在应用，只把 game-agnostic 的机制搬进引擎。
- **先验证再下沉**：0 接线（建了没用）的组件，下沉前先在应用真正接一次、跑通，避免把未验证代码固化进引擎。
- **每项挂测试**：下沉后在引擎侧补/迁测试；替换应用自造件需完整回归 + 并发 `-race`。
