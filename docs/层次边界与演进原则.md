# zEngine 层次边界与演进原则

**版本**：0.0.27

**日期**：2026-09-03

**性质**：zEngine 与上层游戏服务器之间的规范性边界。本文规定“什么可以进入引擎、什么必须留在
应用层、公共 API 如何演进”；事实风险和任务状态分别记录在 zMmoServer 的
`docs/架构审计基线-2026-08-31.md` 与 `docs/架构改进执行计划.md`。

## 一、先保护已经正确的设计

zEngine 的演进服务于现有 zMmoServer，而不是借“通用化”改变它的架构身份。以下上层决定不是
引擎重构的清理对象：

1. realm 是隔离和扩容边界，不改成全区全服；
2. GameServer 是玩家持久资产权威，MapServer 是地图瞬时模拟权威；
3. 每张地图保持 MAP-2 单写者，网络命令和 tick 在同一串行执行域内修改地图状态；
4. 客户端空间可见性只由 MapServer 的 AOI 产生；
5. 分线、普通实例、副本和跨服实例继续复用同一实例池和生命周期原语；
6. 跨服协议继续以 `zCommon/crossserver/codec.go` 为唯一编解码入口；
7. 可靠业务效果使用至少一次投递、全集群唯一幂等键和本地事务原子提交，不用“引擎有类型”
   代替崩溃恢复证明。
8. 普通游戏对象不隐式拥有进程级 worker、HTTP server、signal subscription 或全局 singleton；任何
   会启动 goroutine/ticker/listener 的能力必须有显式 owner 和幂等 Close。

改变底层机制前，先用 characterization test 或跨进程 E2E 固定现有成功路径。引擎优化若破坏上述
任一约束，应视为回归，不视为架构升级。

## 二、四层依赖模型

```text
zMmoServer
  业务策略：realm / Player / Map / 活动 / 权威 / 路由 / 协议 / 事务提交点
      |
zCommon 及各进程适配层
  把业务语义适配到引擎机制；不是第二个通用引擎
      |
zEngine
  运行机制 + 可复用的游戏领域原语；不决定具体游戏的权威和工作流
      |
zUtil
  与游戏服务器无关的容器、加密、并发等通用工具
```

依赖只能向下。zEngine 不得 import `zCommon` 或 zMmoServer；zUtil 也不得知道 zEngine。

“引擎只放 game-agnostic 代码”应按两类理解：

- **基础机制**：网络、并发、生命周期、日志、指标、配置、持久消息存储、lease/CAS/fencing；
- **可复用游戏原语**：AOI、实例池、寻路、脚本运行时。这些可以具有游戏领域用途，但不能带入
  某个项目的 Player/Map/realm/玩法枚举、协议和权威策略。

## 三、能力进入 zEngine 的六道门

新能力或从 zMmoServer 下沉的能力必须同时满足：

1. **语义独立**：公共契约不出现 realm、GroupID、PlayerID、MapID、活动状态、ProtoId 枚举、
   grant 或迁移阶段等应用语义；
2. **机制稳定**：能说清输入、输出、并发归属、超时、取消、过载、持久化和失败语义；
3. **真实使用**：至少有一个上层生产调用者，不以零接线代码或仅有单测作为下沉理由；
4. **依赖单向**：下沉后不产生引擎到应用的反向依赖，也不靠复制业务类型规避依赖；
5. **双层验证**：有引擎侧契约测试，也有真实上层调用链的回归；分布式语义按风险补 E3/E4/E5；
6. **兼容迁移**：先新增兼容 API，再迁真实调用者，搜索确认旧 API 零调用，最后单独删除旧 API。

仅“看起来通用”、能减少目录数量、其他项目也有同名模块，均不是下沉依据。禁止用大规模重命名、
拆服务或制造接口数量来表现架构改进。

## 四、当前依赖事实

生产接线还决定加固顺序：`zInstance.Pool` 是 MapServer 统一实例承重路径；zEvent 的 Map/Chat 全局发布

作为 `zService.ServiceManager` 的一条生产接线；`zConfig.ConfigWatcher`、`zDistributed`、`zScript` 仍无
上层生产构造，`zSignal` 由 zServer 间接使用但无 zMmoServer 直接 import。不得把公共类型成熟度外推为
服务器闭环，也不得只因零直接接线删除包。

约束旧 owner 的写入，两者不能混称。

| `zNavMap` | 通用坐标、图/网格寻路和可取消/有预算的搜索 | 地图配置表、技能移动规则、跨服路由 | 当前无 zMmoServer 生产调用，只能标 experimental；A* 无 context/预算，open node 更新不 `heap.Fix`，g 值、start=end 和路径顺序契约不清；先用真实 AI/移动调用证明需求，再扩 API 和性能承诺 |

AOI 属于引擎原语，但“AOI 是客户端可见性的唯一权威”属于 zMmoServer 的装配约束。引擎负责正确
产生 delta，上层负责只采用这一套 delta，并把 watcher 映射到正确会话。

### 5.5 跨包资源所有权规则

包单独可用，不代表组合后可以任意创建资源。所有 zEngine 能力共同遵守：

1. **进程级资源由进程根拥有**：全局 logger、事件执行器、metrics HTTP server、OS signal 订阅、
   共享 worker pool 只能由 bootstrap/zServer 装配，启动失败时逆序回滚，停止时统一关闭；
2. **实例级资源显式拥有**：确需独立 goroutine/ticker 的实例必须在构造 API 中表达 ownership，提供
   幂等、并发安全的 Close，并由创建者负责调用；普通 Player/GameObject 不默认创建 worker pool；
3. **构造不偷跑生命周期**：New/注册组件只建立对象图，不监听端口、不注册全局 mux、不启动后台循环；
   Start 返回成功必须表示资源已真实取得，异步监听失败必须能回传状态；
4. **引擎锁内不调用上层代码**：build、Occupancy、handler、listener、onEvict、Close 等 callback 在
   明确的锁外阶段执行；若需两阶段状态，用 reservation/generation 保证期间对象不被重复创建或销毁；
5. **全局 singleton 可关闭就必须可重建或明确不可重启**：Close 后仍由 getter 返回的永久关闭实例是
   无效生命周期；测试 reset 也不能依赖修改进程级隐式全局状态；
6. **关闭结果可观察**：Stop/Close 要么返回聚合错误，要么通过状态/事件显式报告；不能只写日志后把
   状态标成 Healthy/Stopped。

上层负责决定资源 scope 和业务停止顺序，引擎负责让每个 scope 的 admission、取消、等待和释放语义
可组合。此规则补充逐包表，不授权把 zMmoServer 的 drain、realm 或实例业务状态下沉进引擎。

## 六、五个跨层争议项的裁决

### 6.1 Envelope 与 codec

当前 `zCommon/crossserver/envelope.go` 的 `Meta` 含 `SourceServerID`、`SourceService`，外层 codec 又含
Game/Map 服务路由和 `BaseMessage.PlayerId/MapId`。因此整个 Envelope 仍是 zMmoServer 的东西向协议
契约，不整体下沉 `zNet`。

若将来至少两个真实协议需要相同能力，可在 zNet **新增**纯机制的 correlation frame，例如 version、
trace、request、timestamp 和 message kind；服务角色、服务器 ID、Player/Map 路由继续由应用 codec
承载。迁移期间旧线格式必须可回放，不能在同一变更里同时改帧、codec 和所有调用点。

### 6.2 discovery

可下沉的是 Registry/Lease/Watch 机制：通用 key、endpoint、metadata、revision、lease、context 和
断线恢复。留在 zMmoServer 的是 `ServerInfo.GroupID/MapIDs/Players`、ServerID 的 realm 编码、服务角色
筛选和分线/容量策略。推荐结构是“zEngine registry + zCommon descriptor/adapter”，不是把现有
`zCommon/discovery` 整包搬走。

### 6.3 ownership

zEngine 提供 owner token、epoch/fencing、revision、lease 和 CAS；zMmoServer 定义 resource kind、
resource ID、状态机以及 handoff/迁移/排空动作。`MigrationManager` 是 MMO 领域工作流，必须留在
zMmoServer，即使它使用 zEngine 的 CAS 和持久消息原语。当前首个适配是 zCommon 定义的
`service-instance/<serviceType>/<groupID>/<serverID>`；它验证通用机制，但不授权把服务身份或状态标签
下沉引擎，也不证明活动分配、Map owner、迁移或排空已经完成。

### 6.4 ID

Snowflake 算法和 `TypedID[Tag]` 基座可在有真实调用后评估进入引擎。当前六位 ServerID 的
`GroupID(4)+ServerIndex(2)` 编码表达 realm 拓扑，必须留在 zMmoServer；PlayerID/MapID 等业务 tag
也留应用层。不得把“整数生成”与“业务身份含义”一起下沉。

### 6.5 Outbox/Inbox

zEngine 只定义消息记录、状态转换、存储错误、事务参与和重试机制。V2 Outbox 以
`Enqueued -> Transported -> Applied` 区分持久入队、传输和业务效果，调用者按自身终态显式
`Complete`；V2 Inbox 以 `Accepted/InProgress/Processed` 区分本次处理权、在途和已完成，存储错误
fail closed。内置 Memory/SQL 遵循同一状态契约，Memory 旧/V2 API 共用转换锁；第三方旧接口适配器
只保源兼容，不能凭适配器获得持久中间状态保证。

应用层仍决定 destination、协议、业务幂等键以及“成功”是入队、写 socket、收到 ACK 还是业务已提交。
现有 `TargetMapID` 等字段和旧 API 通过后续兼容任务逐步迁出，不原地重写公共结构。CON-02 增加的
`SQLExecutor` 只让 store 可绑定调用者持有的 `*sql.DB` 或 `*sql.Tx`，schema 和 commit/rollback 仍由调用者
拥有；zMmoServer 的 Player grant 已用它把 Inbox 与业务写放入同一事务，Map 侧则先持久化 Outbox 意图再
终结瞬时动作。这个机制不定义 grant、ACK 或业务提交点，也不能把传输称为 exactly-once；其它业务路径
仍须逐条证明本地事务和恢复语义。无 durable log 的协调器已按
[ADR-001](ADR-001-进程内事务协调器.md) 收敛为 `InMemoryTransactionCoordinator`：它只保证当前进程内的
并发状态转换和锁外 callback，旧 `TransactionManager` 为 deprecated 兼容名；当前没有生产构造，也不
提供重启恢复、跨进程 fencing 或迁移 commit point。

## 七、公共 API 演进纪律

每项公共 API 改动按固定顺序执行：

1. 记录当前调用图和现有成功路径；先补 characterization test/E2E；
2. 在 zEngine 增加新 API、稳定错误、测试和迁移说明，旧 API 暂时保留；
3. 迁移一个真实 zMmoServer 调用链，完成引擎测试和上层回归；
4. 迁移其余调用者，搜索确认旧 API 无生产调用；
5. 单独标记 deprecated；经过约定版本窗口后再单独删除；
6. 分别记录 zEngine、zMmoServer 的提交和验证证据。

禁止在一个提交里同时完成“引擎 API 重写 + 所有上层迁移 + 旧 API 删除”。对于网络线格式、持久化
schema 和 ownership token，还必须写明回滚和滚动升级策略。

## 八、变更评审清单

评审任何 zEngine 变更时逐项回答：

- 它是基础机制、可复用游戏原语，还是 zMmoServer 业务策略？
- 公共类型是否出现了 realm/player/map/activity/proto/grant/migration 等业务含义？
- 是否至少有一个真实生产调用者，调用点在哪里？
- admission、超时、取消、停止、过载、重试和崩溃后的结果分别是什么？
- 是否破坏 MAP-2、AOI 单一权威、Game/Map 权威分层或 realm 隔离？
- 引擎测试、上层模块测试和所需 E3/E4/E5 分别是什么？
- 旧 API/线格式/schema 如何兼容迁移和回退？
- 文档描述的是当前实现、目标设计，还是仅有实验代码？

任一问题没有答案时，先补证据或 ADR，不进入实现。
